# 🍃 MulleCA

#### 🍃 Animate properties in real time with mulle-objc

MulleCA is used to stuff values into properties over a desired timespan.


If you want a `NSInteger` property named "someIntegerValue"
on your object `foo` to change value from 0 to 1000 over the next second, you
set up a `CABasicAnimation`:

``` objc
   // get property "someIntegerValue" from 'foo'
   property = MulleObjCInstanceSearchProperty( foo, @selector( someIntegerValue));
   // options: NULL yields convenient  default values `delay=0; duration=1;`)
   animation = [[[CABasicAnimation alloc] initWithProperty:property
                                         startIntegerValue:0
                                           endIntegerValue:1000
                                                   options:NULL] autorelease];
   [animation setAnimationObject:foo];
```

and run it with an animator:

``` objc
   animator = [CAAnimator object];
   [animator addAnimation:animation];
   hz       = 60.0;

   while( [animator animateWithAbsoluteTime:time( NULL)
                              animationRate:1.0 / hz])
   {
       struct timespec   delay = { 0, (1000 * 1000 * 1000) / hz };
       nanosleep( &delay, NULL);
   }
   return( 0);
```

## CAAnimator

A `CAAnimator` is used to store and then run `CAAnimation` objects, or rather
objects that conform to the `CAAnimation` protocol.

Simplified, the `CAAnimator` animation loop looks like this:

``` objc
- (BOOL) animateWithAbsoluteTime:(mulle_absolutetime_t) now
                   animationRate:(mulle_relativetime_t) animationRate
{
   for( animation in [self animations])
   {
      [animation animateObject:[animation animationObject]
                  absoluteTime:now
                 animationRate:animationRate];
   }
}
```

In a graphics scenario you would call this method before drawing your graphics,
and you would pass in the current time `now` and the expected `animationRate`
(say 1.0/60.0 for 60Hz). The animationRate is used for quantizing the animation.
If you pass in 0.0, the values will be continuous. Quantizing the animation
ensures, that an accurate final value of the animation is stored in the
property.


## CAAnimationStorage

`CAAnimator` implements the `CAAnimationStorage` protocolclass. The
protocolclass provides methods for the storage of `CAAnimation` objects.

To implement the protocol, `CAAnimator` has to provide an instance variable
for storage and an accessor method for this instance variable:

``` objc
@interface CAAnimator : NSObject < CAAnimationStorageObject>
{
   struct CAAnimationStorage   _animationStorage;
}

- (struct CAAnimationStorage *) animationStorage;

@end
```

## CAAnimationGroup

`CAAnimationGroup` is another class that implements the `CAAnimationStorage`
protocol. It's a passive container for `CAAnimation`s with support for
`CATransaction` transactional animation generation.


### CATransaction

A `CATransaction` is used to generate implicit animations. For this to work
properties must be marked as `observable` and the class must implement the
`CAImplicitlyAnimatableObject` protocol (as the `CAImplicitlyAnimatableObject`
class does):


``` objc
@interface Foo : CAImplicitlyAnimatableObject

@property( observable) CGColor   backgroundColor;

@end
```

The implicit animations are generated by a `CATransaction` and gathered into a
`CAAnimationGroup`:


``` objc
   ta = [CATransaction object];
   [ta begin];
   {
      [layer setBackgroundColor:[UIColor blueColor]];
   }
   group = [ta commit];
```

This is the easiest way to set up animations.


### CABasicAnimation

`CABasicAnimation` is currently the only existing subclass of `CAAnimation` it
is used to animate properties of the following types:

* `NSInteger`
* `NSRange`
* `CGFloat`
* `CGFloat[ 2]`, `CGPoint`, `CGSize`, `CGVector`
* `CGFloat[ 4]`, `CGRect`,
* `BOOL`
* `CGColor`

## Example

``` objc
#import <MulleCA/MulleCA.h>


@interface Foo : NSObject

@property NSUInteger   someIntegerValue;

@end


@implementation Foo

- (void) setSomeIntegerValue:(NSUInteger) value
{
   printf( "%td\n", value);
   _someIntegerValue = value;
}

@end


int   main( void)
{
   CAAnimator                       *animator;
   CABasicAnimation                 *animation;
   Foo                              *foo;
   double                           timestamp;
   struct _mulle_objc_property      *property;

   // create object, get property, create an animation for this property

   foo      = [Foo object];
   property = MulleObjCInstanceSearchProperty( foo, @selector( someIntegerValue));

   animation = [[[CABasicAnimation alloc] initWithProperty:property
                                         startIntegerValue:0
                                           endIntegerValue:1000
                                                   options:NULL] autorelease];
   [animation setAnimationObject:foo];

   /*
    * animator now runs animation with our fake timestamps
    */
   animator = [CAAnimator object];
   [animator addAnimation:animation];

   for( timestamp = 0.0; timestamp <= 1.2; timestamp += 0.2)
      [animator animateWithAbsoluteTime:timestamp
                          animationRate:0.0];
   return( 0);
}
```


## Differences to Quartz CAAnimatio

MulleCA is not a clone of Apples [Quartz CAAnimation](https://developer.apple.com/documentation/quartzcore/caanimation?language=objc),
but tries to be as similar as practical.

A significant technical difference between an Apple CAAnimation and a MulleCA
CAAnimation is, that MulleCA operates directly on the CALayer, whereas Apple
animations operate on a "presentation tree". An Apple animation does not have
a persistent effect on a CALayer. A MulleCA animation actually affects the
CALayer.

Other major differences:

* there is no CAMediaTiming class
* there is no CAKeyFrameAnimation class
* there is no CAPropertyAnimation class
* CAAnimations don't inherit properties from their CAAnimationGroup (currently)
* Setting `autoreverses` does not affect the effective duration of the animation and only comes into effect if the `repeatCount` is greater than 1.
